# Review of docs/plan.md and docs/spike-kwin-tiles.md (2026-10-21)

Independent read. Sources checked: KWin `Plasma/6.7` (`src/window.cpp`, `src/tiles/{tile,tilemanager,customtile}.cpp`,
`src/scripting/{scripting.cpp,workspace_wrapper.h}`, `src/window.h`), i3 `next` (`src/move.c`, `src/tree.c`),
`i3ws/main.js`, the patched Krohnkite `script.js`, the old i3 config (`d3de958^`), README Plasma table, `setup.sh`.
Nothing was run and no repo file was changed except this one.

Overall: the direction (own model, KWin tiles as display, plain JS, tree.js testable in node) is sound, and
the spike was well chosen. But the plan treats the model-to-KWin seam as a projection problem, when the
seam in KWin 6.7 has several behaviours that silently drop or strand windows (findings 1 to 4). Several i3
rules the plan says it ports are stated wrongly (finding 5), and the list of things Krohnkite handles that
must be carried over is thinner than the code shows (finding 8).

Severity: S1 = would break the live session or invalidate a design decision; S2 = will cause visible bugs
in normal use; S3 = under-specified, decide before coding; S4 = minor.

---

## S1-1. Windows lose their tile when KWin moves them between outputs, and a window can sit in a tile that is not "active": hotplug and "move to hidden workspace" are not just re-projection

Evidence:
- `Window::setOutput`-side code at `src/window.cpp` ~3893-3899: when a window changes output and its requested
  tile is a Custom tile, `tileManager(oldOutput)->forgetWindow(this, nullptr)` is called. The window is simply
  untiled, with no signal other than `tileChanged(null)` (which arrives later, see 2).
- `Tile::isActive()` (`src/tiles/tile.cpp:74`) is `m_desktop == currentDesktop(output)`. `Tile::manage()`
  (tile.cpp ~395-420) only calls `window->requestTile(this)` if the tile is active. Otherwise the window is
  added to the tile's list and nothing else happens; its geometry is not set.
  The code comment in `manage` says "or if our desktop is the only desktop the window is in", but the
  code does not test that.
- The spike only tested windows on a desktop shown on the output (`spike-kwin-tiles.md` table). The case that
  matters for i3 semantics is `Meta+Shift+5` (move container to workspace 5) when 5 is not currently shown
  on any output, and a hotplug where outputs disappear. Neither is covered.

Consequences:
1. Plan "Hotplug" risk says "the model keeps each window's workspace and re-projects when the monitor returns".
   While the monitor is gone, KWin's `TileManager` for that output is gone (and the returning output builds a
   fresh one and reads the saved JSON from kwinrc, `tilemanager.cpp::readSettings`, falling back to the 3-column
   default). Windows moved by KWin to the remaining output have lost their tile, and sit on desktop N which the
   remaining output is not showing. The plan does not say where those windows go or what the user sees while
   the monitor is away. i3 has a defined answer (the workspaces of a vanished output move to a remaining
   output and go back when it returns); i3ws's current answer is "ignore the moves for 5 s". Pick one.
2. Moving a window to a hidden workspace means: tile it in a tree whose desktop is not current. It will have
   no geometry until that desktop is shown. The plan needs a "pending" state in the adapter: model says
   leaf L belongs to tile T, KWin has not applied it yet; re-apply on `currentDesktopChanged`.

Fix: make the adapter a single idempotent `reconcile(workspace)`: compute desired tile tree and window
assignment from the model, diff against live tiles, apply. Call it from every event and from
`currentDesktopChanged(prev, cur, output)` and `screensChanged`. Never apply incremental edits. Add live
tests for: move-to-hidden-workspace then show it; output removed then restored (if the virtual backend can't
do that, test `reconcile` against a hand-built "windows lost their tiles" state, which is the same thing).
State in the plan, explicitly, what happens to a vanished output's workspaces.

## S1-2. `tileChanged`, `relativeGeometryChanged` and `outputChanged` are late and noisy; "sizes flow both ways" needs a defined ownership protocol

Evidence:
- `Window::commitTile()` (window.cpp ~3722) emits `tileChanged` when the client has committed the new
  geometry (the `m_tile` vs `m_requestedTile` split), so for Wayland clients it lags our `manage()` call by a
  configure round trip. It is also emitted in `Tile::unmanage` and `Tile::~Tile` paths we cause ourselves.
- `Tile::setRelativeGeometry` (tile.cpp:124-145) emits `relativeGeometryChanged` for every sibling that the
  layout adjusts. One border drag or one `resizeByPixels` is many signals.
- The plan's "something else moved it out of its tile" use of `tileChanged` cannot be told apart from
  "our own unmanage" without bookkeeping, which is the `expectOn` machinery i3ws already needed
  (`i3ws/main.js:expectOn`).

Fix:
- Signals into a QJS script are direct (synchronous inside our setter), so a `syncing` re-entrancy flag
  covers our own relativeGeometry writes. It does not cover `tileChanged`, which is asynchronous for
  clients: keep `expected[windowId] = tile` set by the adapter and clear it when the matching `tileChanged`
  arrives; treat any other `tileChanged(null)` as "user/KWin untiled it" and apply a stated policy (re-tile,
  or float). The plan must state that policy. Cases: interactive move out of a tile (Meta+drag or titlebar
  drag, i3 `tiling_drag modifier titlebar` is in the old config and not mentioned in the plan), maximize,
  KWin quick-tile, output change.
- Read weights back from tiles once, on the *end* of an interactive resize (`moveResizedChanged` /
  `Window.resize` false), not per `relativeGeometryChanged`. Cheaper and avoids feedback.
- Add a plain-JS invariant check (every managed non-floating window is in exactly one leaf; each leaf's tile
  contains exactly that window; no tile is empty) that runs after each reconcile in the live tests and logs
  loudly in production. Exceptions in a signal handler are swallowed per handler by QJSEngine, so without this
  the model and KWin drift apart silently.

## S1-3. `window.tile = x` is deprecated in 6.7; the spike and plan use it

Evidence: `Window::setTileCompatibility` (window.cpp ~3803) logs "Writing to the property window.tile is
deprecated: use tile.manage() instead". The spike scripts (`round2.js:9`, `round3.js:11-12`) all use `w.a.tile = ...`.
The plan's own "KWin's tile API is young" risk is exactly this.

Also `window.tile` reads `requestedTile`, not the committed `m_tile` (`Q_PROPERTY tile READ requestedTile`),
so "tile == null" read right after a change does not mean the client has moved.

Fix: use `tile.manage(w)` / `tile.unmanage(w)` throughout; update the spike notes and re-run the spike
with `manage` before treating "verified" as meaning anything. `Tile::manage` also evacuates the window from
every other tile *of the same desktop on all outputs* (tile.cpp ~395-410) but not from tiles of other
desktops, which is the real cause of spike finding 3 ("desktop change leaves a window in the old tree").
The documented fix is: `oldTile.unmanage(w)` first, then change `w.desktops` / output, then `newTile.manage(w)`.

## S1-4. No story for a script reload or crash with live windows: "rebuild from the windows actually present" discards the tree

Evidence: plan section "KWin events": "At start (and after a reload) every tree is rebuilt from the windows
actually present; trees KWin saved in kwinrc are not trusted." Plan decision 1 sells fast reload
(`unloadScript` + reconfigure) as the main benefit of plain JS.

A rebuilt-from-windows tree loses split structure, orientations, weights, focus stack, and floating state on
every reload. In dev that is acceptable in the headless KWin; in Paul's session a reload (or an exception
that stops the script) re-lays-out every workspace into a flat list. And on unload, windows remain
`requestedTile`d into tiles with nobody driving.

Fix: on start, *read the model back from the live tile tree* (it is the same shape: nested layout tiles with
directions, relativeGeometry as weights, windows in leaves) and take the focus stack from
`workspace.stackingOrder`. Only fall back to flat insertion where a tile holds 0 or >1 windows.
Add a "release" action (shortcut plus D-Bus-invokable) that unmanages every window and restores the default
tile layouts, for the fallback and for a safe unload. Phase 4's fallback ("same three lines reversed and
a logout") should not be the only way back.

## S2-5. Several i3 rules the plan says it ports are mis-stated

Check against `src/move.c` and `src/tree.c`.

1. **"Single-child containers: keep them in the model, as i3 does" (decision 6) is wrong as stated.**
   `tree_move` ends with `tree_flatten(croot)` on every move path (`move.c` end of function, also
   `move_to_output_directed`). `tree_flatten` removes a split container that has exactly one child when the child
   has a different orientation (hoists the grandchild into the parent) and merges same-orientation
   splits. A single-child container only survives where no flatten has run since it was made: right after
   `split h|v` on a lone window, until the next move/close/ref-level operation. Close also reflows
   (`tree_close_internal`). Port `tree_flatten` and its call sites exactly; the tests then pin the precise rule.
2. **`move` has more cases than "insertion after the focused container".** Port these, all in `tree_move`:
   - lone child of a workspace (or fullscreen-output): `move_to_output_directed` straight away;
   - no ancestor with the move's orientation: `ws_force_orientation` (re-wraps the entire workspace in a
     new split of that orientation); this is how `Meta+Shift+Up` on a horizontal workspace works, and is the
     case most likely to be written wrong from memory;
   - sibling is a container: move *into* it via `con_descend_direction` with the AFTER/BEFORE rule shown in
     the source, otherwise swap with a leaf sibling;
   - at the edge of the nearest same-orientation ancestor: step up a level and repeat, then insert beside
     the ancestor or into the adjacent branch;
   - the "lone child of a non-default layout container at the workspace edge" branch (irrelevant until tabbed/stacked).
3. **Cross-monitor move target is the *visible* workspace of the neighbouring output**
   (`move_to_output_directed`: `GREP_FIRST(ws, ..., workspace_is_visible)`, then `attach_to_workspace(con, ws, direction)`,
   which places by direction). The plan's table says "crosses to the other monitor's workspace, landing on the side it came
   from" which matches, but the plan's model has no notion of "output" other than `Workspace.output`; `get_output_next(CLOSEST_OUTPUT)` is geometric.
   State that `screenToward` (i3ws) is the port.
4. **Focus direction is tree-based in i3 (`tree_next` / `con_descend_focused`), not geometric.** i3ws's
   `neighbour()` is geometric and works with Krohnkite's layout. The plan never says which one kwin-i3 uses.
   With a model, port i3's: walk up to the nearest ancestor with the right orientation, take the sibling,
   descend by the focus stack (`focus_head`). The two disagree for nested splits (i3 returns the most recently
   focused leaf of the neighbour branch, not the geometrically closest). The README "must be kept" is "as in i3",
   so use i3's.
5. **Where new windows go** is only stated in decision 5. The details matter: new tiled window is inserted
   after the focused *container* of the workspace of the *focused window*, not of the output the window
   appears on, and an unfocused/background-opened window (focus stealing prevented) still goes after the focus.
   KWin picks the output itself (active screen or under pointer) and i3ws then assigns the desktop of `w.output`,
   so the model's workspace is determined by KWin's placement, not i3's. Say so, and make `windowAdded` read
   `w.output` once the window is ready (see 7).
6. **Closing**: focus after close follows the focus stack of the parent (`tree_close_internal`, `con_activate(next)`),
   and i3's `focus` goes to the previous focus in that container, not the geometric neighbour. The model owns
   this, but `windowActivated` events from KWin's own choice (focus follows mouse) also write the focus stack.
   The plan has no rule for which wins; i3 has the same interaction and it is "the last focus event wins". Fine,
   but write it down, and note that `FocusFollowsMouse` plus a re-projected layout will move focus under a
   stationary pointer.
7. **Fullscreen**: KWin fullscreen on a tiled window works (spike), but i3 semantics when a second window
   opens or a move is attempted on a fullscreen workspace (`con_fullscreen_permits_focusing`, "Not moving
   fullscreen global container" in `tree_move`) are not covered. Decide: move/focus keys are no-ops while the
   focused window is fullscreen, or leave fullscreen first.
8. **Not planned but in the spec (old config)**: `focus parent` is out, fine, but also `Meta+Shift+C/R/E`
   (reload/restart/exit) have no mapping, and `urgent` (i3 `urgent` hint / KWin `demandsAttention`) has none.
   With no panel, an urgent window in a hidden workspace is currently invisible; i3 would show it in the bar.
   Write WON'T-FIX with reason or ask Paul.

## S2-6. Tile minimum size is not derived from windows; windows will overflow tiles

Evidence: `setMinimumSize` is only ever called from scripts (`grep` over `src/tiles/*.cpp`: only the setter
definition at `tile.cpp:262`). `Tile::setRelativeGeometry` clamps to the tile's own minimum, which is 0 by
default. A window clamps itself to its `minSize` (`window.cpp:4152-4156`). So a window whose minimum is larger than its tile
simply overflows over its neighbour, and a border drag can shrink a tile below what the window accepts.
Krohnkite has code for this (`script.js` ~609-734, `minSize`-aware sizing; `commit` clamps to
`minSize`/`maxSize` at ~1900-1906), and the plan lists it only as an unmet risk.

Fix: when a window is ready, set the `minimumSize` of its leaf tile to `w.minSize`, and propagate up
(`parent.minimumSize` = sum along the layout direction, max across). Or decide the policy: float any window
whose min size cannot fit (Krohnkite's closest analogue). Add to phase 2 with a live test client that sets
a large `xdg_toplevel.set_min_size`. Alacritty is the only test client in the spike; you need at least
one fixed-size and one dialog/transient client. A tiny Python or Qt client written for the harness is enough.

## S2-7. `windowAdded` fires before the window is ready; classification needs a second step

Evidence: Krohnkite's `addWindow` guards on `client.pid >= 0`, `!client.hidden`, `client.width*client.height > 10`,
`!client.popupWindow`, `client.normalWindow` (script.js ~1335-1360) and then relies on later events; `Window.h`
has `readyForPaintingChanged`. `minSize`, `transient`, `resizeable`, `windowType` and `caption` (the Xephyr
title rule!) may not be final at `windowAdded`. The plan's "Which windows float" list has no timing.
Also the plan's list mixes categories: dialogs, utility, splash, notification are not `normalWindow` at all
(`window.h` `normalWindow READ isNormalWindow`), so they are never candidates; the floating decisions that
actually need work are `transient`, `modal`, `!resizeable`, `skipPager` (Krohnkite `floatSkipPager`), caption/class
rules, and `activities`.

Fix: classify on `windowAdded` if ready else on `readyForPaintingChanged`, and re-classify on
`captionChanged`/`windowClassChanged`/`transientChanged` (Xephyr's title is set after map; Steam and many
Electron apps open as one window and re-parent). Use `!resizeable` (what Krohnkite uses) in preference to
"min == max". Carry over Krohnkite's default `ignoreClass` list verbatim as a starting point
(`script.js:1236`: krunner, yakuake, spectacle, plasmashell, ksplashqml, polkit agent, kruler, ...) and the
`floatingTitle` setting from `setup.sh:168`.

## S2-8. Gaps versus Krohnkite and i3ws that the plan does not list

From `script.js` and `main.js`; each is either carried over, dropped on purpose (with a reason), or asked.

- **Layers**: Krohnkite sets `keepAbove` for floating vs tiled (`commit(... windowLayer)` ~1843-1847,
  `tiledWindowsLayer`/`floatedWindowsLayer`). i3 keeps floating windows above tiled. Plan has no floating stacking rule.
- **Maximize**: Krohnkite un-maximizes on add (`script.js:1355`) and on change. Plan says "undone"; spike
  shows maximize drops the window from its tile, so you must re-`manage` after un-maximizing; also covers
  window rules that force maximize (`requestTile` returns early if the maximize can't be cleared, window.cpp ~3770).
- **Activities**: Krohnkite filters by activity (`script.js` ~1575, 1768-1793). Paul has one activity, but
  `windowList()` includes all activities' windows and i3ws's `visible()` ignores them. Decide "single activity,
  ignore" and write it down.
- **Windows on all desktops / sticky**: i3ws's `managed()` excludes `onAllDesktops` and `skipTaskbar`. Keep
  exactly that, and say so.
- **Minimized windows**: i3ws `visible()` excludes minimized; the model needs "minimized = out of tree"
  (and back in at the same place?) or "stays in tree and is just not shown". i3 has no minimize. Paul's README
  says no minimise key exists, but Overview can minimise: pick.
- **No-border handling**: `i3frame` plus `BorderSize=Tiny` carry the look; Krohnkite also managed `noBorder` for sole windows
  (`soleWindowNoBorders`, off by default). Not needed, confirm.
- **Mouse warp**: i3ws's pointer-follows-focus-across-monitors (`MoveMouseToFocus` / `MoveMouseToCenter` via
  `callDBus` to kglobalaccel). Plan keeps it ("pointer follows focus") but the live test harness has no pointer.
- **Login numbering and the activity-restore re-numbering** (`numberedAfterActivity`, i3ws main.js) are a
  fragile bit of startup timing that the plan folds into "merged in rather than called". It needs its own
  test or a manual checklist item in phase 4.
- **Screen-change handling**: i3ws tracks `lastOutput`, `knownScreens`, a 5 s `screensChangedAt` window, and
  `expectOn`. These are the scar tissue from the 2026-10-21 monitor-wake bug; the plan's hotplug mitigation is
  one sentence. Port the test cases (monitor sleep/wake sequence from the log) before deleting that code.
- **Persisted tile config**: tile padding and trees live in `kwinrc [Tiling]`. New roots (new desktop, new or
  returning output) start with padding 4 and a 3-column layout (`tilemanager.cpp::readSettings`,
  `createDefaultSetup`). The script must set `padding = 0` on every root it sees *and* on future ones
  (`desktopsChanged`, `screensChanged`), or set `[Tiling] padding=0` via `setup.sh` `kset` as well. Also KWin's
  own tile gestures (Shift-drag to tile, Meta+arrows quick-tile) must stay unbound; the README keep-list already
  unbinds shortcuts, but drag-to-edge quick tiling is an option in Window Management and should be checked.
- **Shortcut plumbing**: `setup.sh` (lines ~238-260) waits for `KrohnkiteI3wsToFront` and `i3ws Workspace 1`
  and prunes all other shortcuts. Phase 5 must replace those names, and `tests/test-claude-config.sh` and
  `health-check` assert on them. Script-registered shortcuts get persisted in `kglobalshortcutsrc` under
  the *script's* action names; renaming actions leaves dead entries. Choose final names now.

## S3-9. API assumptions: what is right, what the plan should add

Checked against 6.7 headers and `scripting.cpp`:
- `windowAdded`, `windowRemoved`, `windowActivated`, `screensChanged`, `currentDesktopChanged(previous, current, output)`
  (per-output; exactly what the plan's "per-screen current desktop change" needs; i3ws never used it, it polls) all
  exist on `workspace`. Window: `desktopsChanged`, `outputChanged(oldOutput)`, `fullScreenChanged`, `maximizedChanged`,
  `minimizedChanged`, `tileChanged(tile)`, `demandsAttentionChanged`, `readyForPaintingChanged`, `moveResizedChanged`,
  `captionChanged`, `transientChanged` all exist. `relativeGeometryChanged` is a `Tile` signal. Good.
- **`QTimer` is available in plain-JS scripts** (`scripting.cpp:217-219` registers a `ScriptTimer` metaobject as global
  `QTimer`); the plan never mentions timers, but debouncing `screensChanged` and deferring `reconcile` to the end of an
  event burst needs them. Prefer one coalescing `QTimer` with interval 0 over `Date.now()` windows (the i3ws 5 s
  hack is a stand-in for it).
- `registerShortcut` and `callDBus` (also with a callback) are available in plain JS (used by i3ws today). There is
  **no way to unregister a shortcut or add one at runtime from a script**, so the `resize` *mode* (plain `j k l ;`
  keys active only in the mode) is not buildable as a mode. Take scope-question-2's second option now:
  `Meta+Ctrl+arrows` (and `Meta+Ctrl+j/k/l/;`). A registered but disabled key trick does not exist.
- Hot-reload via `unloadScript`: shortcuts registered by the unloaded script are dropped, but persisted
  bindings in `kglobalshortcutsrc` stay. Fine, but the test harness uses a private config so cannot catch
  a stale-shortcut regression in Paul's session.
- `workspace.rootTile(output, desktop)` for a desktop that isn't current: confirmed present in the header
  (`workspace_wrapper.h:401`). Tile signals `windowAdded`/`windowRemoved` in the plan's API table are
  `Tile.windowAdded/Removed`; `Tile` also connects `Workspace::windowRemoved` to its own `unmanage`
  (`tile.cpp:34`) so closed windows leave tiles by themselves; you only remove the empty tile.
  Do that in the same `windowRemoved` handler after KWin's (order of slot invocation is connection order; KWin's
  connection was first, so safe, but assert it in a live test).
- `Tile.remove()` on a `CustomTile`: removing a tile moves its windows to `root->pick(window centre)`
  (`tile.cpp::~Tile`), not to the sibling the spike observed generally. The spike's "into the sibling" holds only
  when the geometry puts the window centre there. Do not rely on it; always unmanage first.

## S3-10. Testing and phasing

What is good: node tests of `tree.js`; headless KWin with private bus; the mutation-first discipline; "never load
into Paul's session while the old pair runs".

What is missing or unrealistic:
1. **Test clients.** The spike uses Alacritty with `LIBGL_ALWAYS_SOFTWARE=1`; it can't be a fixed-size window,
   a dialog (transient), a window with a large min size, a slow-to-map window, or one that resizes itself.
   Write one tiny client (Python with `pywayland`, or a Qt/GTK program) with flags for those; without it,
   S2-6 and S2-7 can't be tested and phase 2's "floating rules" has nothing to run against.
2. **`invokeShortcut` for script shortcuts** goes to component `kwin` with the action's objectName, as i3ws's own
   `invoke()` does; fine. But it needs `kglobalaccel` on the private bus, which the harness has to start (the
   plan notes ksecretd/portals were activated on the private bus; check kglobalaccel is among the services
   the private bus activates, and that registering the same shortcut names in the private config can't
   touch Paul's `kglobalshortcutsrc`; `XDG_CONFIG_HOME` is redirected, so it should not).
3. **Input-dependent behaviour cannot be tested headless** (focus follows mouse, pointer warping, border drag,
   titlebar drag). The plan defers the border drag to phase 4. Add `FocusFollowsMouse` interplay and
   interactive move/untile to that list; they are the likeliest places for a surprise (S1-2).
4. **Phase 3's hotplug test** is described as "an open question". If the virtual backend cannot unplug an
   output, build the S1-1 `reconcile` so that it can be driven by a synthetic "windows lost their tiles
   and output set changed" state, and test that. Hand-testing hotplug on Paul's session is exactly the 2026-10-21 failure.
5. **Phase 4 switch-over**: three kwinrc lines plus a logout is fine, but a logout is a lot of friction for a "try it".
   Because Krohnkite is QML, you could instead *test kwin-i3 in a nested session first*: run a second
   full Plasma session on a different VT or `kwin_wayland --x11/--wayland` nested window with real clients
   and a real compositor config, avoiding the live session entirely. The plan's only real-input stage is Paul's
   own desktop. Consider a nested `kwin_wayland` with `--output-count 2` window for a day of dogfooding of
   mouse behaviour (can be launched with a visible window; this does not touch the live session, but it does
   put a window on it, so ask Paul first).
6. **Safety valve**: add the "release all tiles" action (S1-4) and an env/kwinrc switch `kwin-i3Enabled=false`
   that is also honoured at runtime (poll `readConfig` on `configChanged`? scripts get `workspace.configChanged`?
   not guaranteed; simpler is a registered shortcut `Meta+Ctrl+Shift+Q` that releases tiles and sets a
   disabled flag).
7. **Reaction to errors**: wrap every signal handler in try/catch that logs and triggers a `reconcile`; the
   log sink over D-Bus exists already (`tools/logsink.py`) because `print` is dropped here; keep that in production
   mode behind a config flag so a field failure can be debugged.
8. `build.sh` concatenation loses file/line info in KWin's error output; keep a `// ---- src/foo.js` marker
   comment at each file start and have `build.sh` emit a line map.

## S3-11. Simpler options worth weighing

1. **Do not model what KWin already models.** The tile tree already is the container tree (nested layout tiles with
   direction and relative size, windows in leaves). The model is needed for: focus stack, single-child
   containers between operations, `tree_move` rules, floating set, and workspace/output ownership. A thinner
   design: *tiles are the structure; the script adds only the focus stack and ops*, implementing `tree_move` as
   operations on the tile tree (read tiles, compute the target, `unmanage/manage`/`split`/`remove`). This removes the
   whole model-to-tile projection and the S1-4 recovery problem, at the cost of being unable to unit-test in node
   without a fake tile API. A fake of ~100 lines (Tile with tiles/windows/parent/split/remove/manage) in the test
   harness recovers node testing. This is a real alternative; the plan rejects "KWin's tiles as the truth" on the
   basis of four differences, but three of them (empty tile, collapse, halving) are all handled by the same
   few lines of "after every op, normalise" and the fourth (desktop change) is handled by the manage order in S1-3.
   I would still go with the model if you intend to port i3's flatten/move exactly, but make it a conscious choice;
   at minimum, make `reconcile` read the tiles (S1-4) so both are in step.
2. **Reuse more of i3ws as is.** Workspaces, login numbering, pointer warping and hotplug guards are not
   related to the tree; keep them as a separate source file with their existing logic and add tests around them,
   rather than "merged in". Only the pieces that call Krohnkite (`KrohnkiteShift*`, `KrohnkiteI3wsToFront`) change.
3. **Resize**: instead of mirroring `relativeGeometry` back into weights, let tile geometry be the only store
   for sizes (weights = tile relativeGeometry), and keep weights out of the model except as the initial equal split
   on insert/remove (needed because `split` halves, spike difference 5). Eliminates the "sizes flow both ways" problem.

## S4. Smaller points

- Plan "Layout of the repo": `src/keys.js` "matching README": the README that matters is the dotfiles README
  Plasma table; the kwin-i3 README has no key table. Say which.
- The plan says fullscreen "stays KWin's own" via Meta+F and `Window Fullscreen`. That action is a kglobalaccel action in
  `kwin`, so the adapter does not see the key, only `fullScreenChanged`; fine, but then fullscreen on a *floating*
  window and on a leaf with siblings must both be tested.
- Spike table row 1: "live session, read only, no window is in a tile" was a read-only dump; fine. But note the live
  trees hold the 3-column default and the saved JSON includes it; when kwin-i3 clears and rebuilds roots it
